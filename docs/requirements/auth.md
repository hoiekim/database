# `auth` — inventory of Postgres usage (requirements for the replacement database)

Source tree: `the auth repository`. Two servers that must behave the same and can run **side by side on one database**:

- Rust (primary, the future): `rust/src/**` — `tokio-postgres` 0.7 + `deadpool-postgres` 0.14, rustls.
- Bun/TypeScript (cross-check): `src/**` — Bun's built-in `SQL` client (tagged templates), no dependencies.

Both apply the **same** migration files (`src/migrations/*.sql`; the Rust binary embeds them through `rust/build.rs`). Every statement in the Rust tree has a 1:1 counterpart in the TS tree; the few textual differences are listed in §2.0. All references are `file:line`; Rust first, TS in parentheses.

How the app talks to the database (applies to everything below):

- Hand-written SQL with positional parameters; no ORM, no query builder. Rust wrapper `Q::{Pool,Tx}` (`rust/src/db.rs:134-179`) offers `query` (rows), `first` (0..1 row), `one` (exactly one row, else error `NoRowError`), `execute` (affected-row count). Every statement is prepared and cached per connection (`prepare_cached`).
- Parameter types bound from Rust: `text`, `bytea`, `text[]`, `int4`, `int8`, `float8`, `bool`, `timestamptz` (chrono `DateTime<Utc>`), and NULL for any of them (`Option<T>`). JSON, IP addresses and some timestamps are bound **as text and cast in SQL** (`$n::text::jsonb`, `$n::text::inet`, `$n::text::timestamptz`).
- Result types read: `text`, `bool`, `int4` (all counts are `count(*)::int`), `int8`, `timestamptz`, `bytea`, `text[]`, `jsonb` (as `serde_json::Value`), nullable variants of each.
- No stored procedures, triggers, views, enum types, extensions, LISTEN/NOTIFY, full-text search, window functions, CTEs, UNION, OFFSET, TRUNCATE, savepoints or explicit isolation levels are used anywhere (verified by grep over both trees).

## 1. Schema

21 tables: 17 from `src/migrations/0001_initial.sql`, 3 from `src/migrations/0002_services.sql`, plus `schema_migrations` created by the migrator (`rust/src/migrate.rs:17`, `src/migrate.ts:19`). The design's copy of the DDL is `docs/DESIGN.md:517-721`. No schema qualification is used in any statement: the schema is whatever `search_path` selects (the test harness runs each stack in its own schema through `?options=-c search_path=<schema>`, `conformance/harness.ts:990,1028`).

Global facts:

- **Extensions:** none. **Triggers:** none. **Enum types:** none (enumerations are `text` + `CHECK … IN (…)`). **Domains/views/functions:** none.
- **Sequences:** two, both implicit from `bigserial`: `outbox_id_seq`, `audit_id_seq`.
- **Server-generated values:** only the two `bigserial` ids and `DEFAULT now()` timestamps. Every other id is generated by the app: `<prefix>_<26 lowercase Crockford-base32 chars of a UUIDv7>` (`rust/src/crypto.rs:75`), e.g. `usr_…`, `ses_…`, `inv_…`, `apw_…`, `key_…`, `pk_…`, `evt_…`. Ids therefore sort by creation time as ASCII text, which the keyset pagination relies on.
- **Types in use:** `text`, `timestamptz` (microsecond; the app prints millisecond, truncating — `rust/src/util.rs:28`), `bytea`, `bigint`, `int`, `boolean`, `text[]`, `inet`, `jsonb`, `bigserial`.
- **Every PRIMARY KEY / UNIQUE constraint is a btree unique index** with Postgres's default name (`<table>_pkey`, `<table>_<col>_key`). Two of those names are matched by the app in error handling: `users_username_key` and `users_email` (§3.4).

## 2. Query catalogue

171 distinct statement shapes, numbered Q1–Q171. "CAS" marks a conditional write whose affected-row count or `RETURNING` the app relies on.

### 2.0 Rust vs TS differences (all cosmetic; behaviour is the same)

- **Column lists:** Rust names columns (`USER_COLUMNS`, `rust/src/users.rs:45`, "so a column a later migration adds changes no prepared statement's result"); TS uses `SELECT * FROM users` (`src/users.ts:69,79,80`, `src/api.ts:482,517`).
- **Lists:** Rust binds one `text[]` and writes `= ANY($1)`; TS expands a list, `IN ${sql([...])}` (`src/imports.ts:162,166,272`, `src/registry.ts:236,274,276,334,336`).
- **Casts:** Rust `$n::text::inet`, `$n::text::timestamptz`; TS `${x}::inet`, `${x}::timestamptz`. Arrays in TS go through `tx.array(v, "TEXT")`.
- **Session load:** TS selects two more columns (`extract(epoch FROM s.auth_time)::bigint AS auth_time`, `u.email_verified_at IS NOT NULL AS email_verified`, `src/sessions.ts:39`); Rust reads them later (Q61, Q4).
- **Audit cursor:** Rust `($2::bigint IS NULL OR id < $2)` with `id` read as `int8`; TS `(${after} = '' OR audit.id < ${after||"0"}::bigint)` and `SELECT id::text` (`src/api.ts:908`).
- **Revision:** TS reads `revision::text` (`src/registry.ts:29,51`); Rust reads `int8`.
- **Re-encryption:** Rust aliases columns (`AS id`, `AS sealed`, `rust/src/rekey.rs:24-32`); TS does not.
- **Migration runner:** TS `sql.reserve()` + `conn.begin` + `tx.unsafe(text)`; Rust `batch_execute("BEGIN")` … `batch_execute(text)` … `COMMIT`.

## 3. Transactions and concurrency

### 3.1 Mechanics

- A transaction is `BEGIN` … `COMMIT` on one pooled connection (`rust/src/db.rs:186-258`; TS `sql.begin`, `src/tx.ts`). **No isolation level is ever set: everything runs at Postgres's default READ COMMITTED**, and the CAS statements depend on its behaviour — a second writer blocks on the row lock, then re-evaluates its `WHERE` against the committed row and matches nothing.
- No savepoints, no nested transactions, no `SET LOCAL`, no deferred constraints.
- Any error inside a transaction ends it: the caller always rolls back (`Tx::finish`, `rust/src/db.rs:232`). The app never continues after a failed statement.
- A failed `COMMIT` is followed by `ROLLBACK` and surfaces as an error (`rust/src/db.rs:213`). A `Tx` dropped without commit (request cancelled, handler panicked) rolls back in the background (`rust/src/db.rs:246`).
- **Effects after commit:** emails and alert webhooks are queued with `tx.after(…)` and run only once the commit succeeded (`rust/src/db.rs:207,218`) — the client API must make "committed" an explicit, reliable outcome.
- Inside a transaction every statement uses that transaction's connection, including the signing-key cache refresh (`rust/src/keys.rs:69-73`: "waiting for another pool connection while holding one could wedge the pool").
- Outside a transaction each statement is autocommit on any pooled connection; a statement issued after a commit must see it (e.g. Q44 right after the insert's commit, `rust/src/api.rs:416`).
- `now()` is the transaction's start time, constant within a transaction, and one statement's time in autocommit. Nothing depends on it advancing inside a transaction.

- `rust/src/cli.rs:216,247,268,285,304` — create user (+ grants + token), clear MFA, enable/disable, reset link, client secret / retire.
- `rust/src/imports.rs:298` import users — **up to 10,000 × (Q12, Q129, grants, Q106) in one transaction**; `:460` import API keys — Q159 then up to 10,000 × (Q89, Q129). All-or-nothing is the contract ("write all or nothing").

Deliberately *not* transactional (independent autocommit statements): the password sign-in check (Q133, Q2/Q3, Q134, Q135, Q129, Q31), introspection (Q91, Q133, Q138, Q86, Q87), session load and touch (Q52, Q53), passkey assertion (Q42, Q137, Q43), outbox delivery (Q123 then per-row Q124/Q125/Q126), the health ping.

### 3.3 Locks

| lock | where | purpose |
|---|---|---|
| Session-level advisory lock, blocking, explicit unlock (`'auth.migrate'`) | Q165, `rust/src/migrate.rs:14,48` | Two processes starting together apply each migration once. Released if the holder's connection dies. |
| Transaction-level advisory lock, **try** (`'auth.housekeeping'`) | Q166, `rust/src/jobs.rs:22` | Housekeeping runs in one process at a time; the others skip the pass. |
| Transaction-level advisory lock, blocking (`'auth.keys'`) | Q167, `rust/src/keys.rs:174` | Key rotation is serialized; the loser waits, then finds nothing to do. |
| Transaction-level advisory lock, blocking, keyed per entity (`'family:<id>'`) | Q167, `rust/src/sessions.rs:147` | Serializes everything that ends or extends a refresh-token family, "taken before any of its rows is locked: otherwise a rotation in flight could insert a token an ending UPDATE never sees" — i.e. it guards against **phantom inserts**, which row locks cannot. |
| Global write mutex via a single-row UPDATE | Q142, `rust/src/registry.rs:145` | "serializes every change to the services, and makes every copy reload them at its next request". |
| Row `FOR UPDATE` | Q22 (access row; no lock when absent — the upsert covers that), Q148/Q153 (service), Q149/Q154 (its clients, in a fixed order), Q69 (`FOR UPDATE OF r` on a LEFT JOIN), Q37/Q120 (re-encryption) | Read-modify-write. |
| Row `FOR SHARE` | Q159 (service), Q160 (client) | A grant, invitation, credential or token transaction pins the definition it was checked against until it commits; many can hold it at once, and a change (Q148/Q149/Q150/Q151/Q155) waits for them, or they for it. |
| `FOR UPDATE SKIP LOCKED` | Q123 | Concurrent processes never lease the same outbox rows in the same pass. |
| Implicit | FK checks (key-share lock on the parent), unique-index insertion waits, cascade deletes | E.g. inserting `access` for a user being deleted. |

Advisory keys are `hashtext(<string>)` (a 32-bit hash, so unrelated families can share a lock — harmless); both servers must derive the same keys (DESIGN §16).

**Lock ordering is designed, not detected.** Deadlocks (40P01) are never caught; the code avoids them: the client row (Q160) is "taken first in a token grant's transaction, before any refresh-token lock" (`rust/src/registry.rs:472`); the service row before the invitation row (`rust/src/invites.rs:105`); the family advisory lock before any family row (`rust/src/sessions.rs:144`); Q142 first in every services change.

### 3.4 Errors the app relies on

Only **unique violation, SQLSTATE 23505**, optionally with the **constraint name** (`rust/src/error.rs:58-62`; TS `errno === "23505"` and `.constraint`, `src/users.ts:63-65`):

| where | constraint | what the app does |
|---|---|---|
| Q12, `rust/src/users.rs:151` | `users_username_key` | 409 "That username is taken."; the caller's transaction rolls back whole |
| Q12, `rust/src/users.rs:152` | `users_email` (the partial unique expression index, reported as the constraint) | 409 "Another account uses that email address." |
| Q16, `rust/src/api.rs:826` | any | 409, rollback |
| Q19, `rust/src/pages/flows.rs:707` | `users_email` | 409 page; the token consumption rolls back with it |

Sign-up and invitation pages turn the 409 into a page (`rust/src/pages/flows.rs:159,275`); the user import reports it as "writing failed (PostgresError)" (`rust/src/imports.rs:199`). Every other uniqueness case is handled without an error, through `ON CONFLICT` (Q24, Q32, Q41, Q133, Q135, Q137) or a pre-check under a lock (Q143, Q145 under Q142).

Not caught anywhere (they become a 500 and a rollback): serialization failure 40001 (cannot occur at READ COMMITTED), deadlock 40P01, foreign-key 23503, check 23514, not-null 23502. `CHECK` constraints are a backstop only; the app validates first. "No row" from a `one()` is a programming error (`NoRowError`).

### 3.5 Retries and timeouts

- **No statement is ever retried.** The only retry loops are start-up (migrate → checks → key rotation → load keys, retried every `min(1 s × attempt, 10 s)` until the database answers; `rust/src/main.rs:181-206`) and the periodic jobs (next tick).
- Connect timeout 30 s by default (`connect_timeout` in the URL; `0` = none), applied to the socket and to pool creation (`rust/src/db.rs:62-74,90`).
- Optional `idle_timeout` / `max_lifetime` from the URL: a connection past either is closed when next taken (`rust/src/db.rs:91-105`).
- No statement timeout or lock timeout is set by the app; a deployment may pass `statement_timeout=…` (or any server setting) as a URL parameter, which is sent at connection start (`docs/DEPLOYMENT.md:157-159`).
- No timeout on waiting for a pool connection.
- Health ping: `SELECT 1` answered within 2000 ms or reported unhealthy; at most 2 pings in flight, callers share one (`rust/src/db.rs:260-311`, `rust/src/app.rs:85`).
- Outbox lease 60 s (Q123): a process that dies mid-delivery leaves the row to be retried after the lease.

## 4. Other server features

1. **LISTEN/NOTIFY — not used.** (DESIGN §7.4 only suggests it to *apps*.) Cross-process propagation is by polling: Q140 every request, Q114 every 60 s, Q123 every second.
2. **Full-text search — not used.** Search is Q7/Q8: prefix `LIKE` on `username`, `lower(name)`, `lower(email)` with `\`-escaped metacharacters, no supporting index (scans).
3. **Sequences.** `audit.id` and `outbox.id`. `audit.id` is exposed as the API cursor and as "newest first" (Q130); `outbox.id` orders delivery (Q123). Gaps are fine; values must be unique and roughly chronological. Tests insert explicit ids far above the sequence (`conformance/admin.test.ts:1442`).
4. **Server-side time is the system's one clock.** Every expiry, lease, window, rotation date and age is computed from `now()` in SQL (`rust/src/sessions.rs:30`: "by the database's clock"), so processes need not agree on time. Needed: `now()`, `now() ± interval` with seconds as a float (`make_interval(secs => $f64)`) and days as an int, interval literals (`'1 minute'`, `'1 hour'`, `'1 day'`, `'7 days'`, `'30 days'`, `'89 days'`), `extract(epoch FROM …)`, `ceil`, `power`, `LEAST`, `GREATEST`, timestamp difference. App-clock exceptions: `users.email_verified_at` at insert and `users.disabled_at` (`rust/src/users.rs:142,164`), JWT `iat`/`exp`, TOTP steps, the outbox give-up age read from the token (`rust/src/events.rs:134`).
5. **Timestamp parsing by the server.** API-key expiry and imported timestamps arrive as text and are parsed by Postgres (Q83, Q89, Q169, Q170). The app pre-filters the shape and leaves calendar validity to Postgres ("30 February … Postgres knows better", `rust/src/credentials.rs:212`). Shapes the app lets through to the server's parser: `YYYY-MM-DDTHH:MM[:SS[.fraction]]` with `Z`/`z`, `±HH:MM`, `±HHMM` or no zone (which Postgres reads in the session time zone), and `24:00[:00]` (`rust/src/credentials.rs:142-185`); the server must then reject impossible calendar dates such as 30 February or 29 February in a common year, convert offsets to UTC and keep fractional seconds (`conformance/me.test.ts:1485-1522`). The import path (Q89) validates fully in the app first (`rust/src/imports.rs:73-112`), so there the server only converts.
6. **Server-generated ids:** only the two sequences. `DEFAULT now()` is relied on for every `created_at`/`granted_at`/`at`, for `sessions.last_seen_at`, and for `outbox.next_attempt_at`; `DEFAULT 0` for `outbox.attempts`.
7. **`bytea`.** SHA-256 digests as primary/unique keys (`sessions.token_hash`, `refresh_tokens.token_hash`, `auth_codes.code_hash`, `one_time_tokens.token_hash`, `credentials.secret_hash`, `invites.token_hash`, `client_secrets`, `recovery_codes`), a variable-length unique key (`passkeys.credential_id`), and small opaque blobs (`totp.secret_enc`, `signing_keys.private_key_enc`, `passkeys.public_key`). Operations: equality, `IN`, `<> ALL`, `encode(…, 'hex')`. All under ~1 kB.
8. **JSONB.** `audit.detail` (written from text, returned whole, one field extracted in Q131) and `signing_keys.public_jwk` (written and returned whole; served verbatim as the JWKS). JSONB normalizes objects (key order, duplicate keys), so what the API returns has Postgres's key order, not the writer's.
9. **Arrays (`text[]`).** Nine columns (§1). Ordered, read and written whole. The only array operations: `col <> '{}'` (Q156) and `scalar = ANY($array_parameter)`. No containment, unnest, or array indexes.
10. **`inet`.** `sessions.ip`, `audit.ip`: written from the app's text form, read back with `host(ip)`, never compared or range-queried. The output is Postgres's canonical text for the address.
11. **Collation and case folding.**
    - Email uniqueness and lookup are defined by Postgres's `lower()` (Q2, Q5, Q8, Q10, Q18, index `users_email`), whose result for non-ASCII letters depends on the database's locale.
    - The app also lowercases on its own side (Rust `to_lowercase()`: the LIKE pattern in Q7/Q8, the email list in Q10, `same_address` in `rust/src/pages/flows.rs:297`, throttle keys) and compares the two; they agree for ASCII and may not for other scripts. The replacement should offer one defined case-folding function used on both sides.
    - `LIKE` is case-sensitive; usernames are lowercase ASCII by `CHECK`.
    - `ORDER BY` on text relies on the database collation for `id` columns (lowercase ASCII, so any collation gives byte order), `service`/`role`/`name` (lowercase ASCII with `-`), `kid` (mixed case; order only needs to be stable), and the keyset comparisons `id > $cursor`.
    - Text cannot hold NUL in Postgres; the app strips or refuses it itself (`rust/src/throttle.rs:12-16`, `rust/src/users.rs:114`, `rust/src/server.rs:141-144`).
12. **Cascading deletes the app relies on.**
    - Deleting a **user** (Q20) removes its `access`, `totp`, `passkeys`, `recovery_codes`, `sessions` (and through them `refresh_tokens` and `auth_codes`), `refresh_tokens` by `user_id`, `credentials`, `one_time_tokens`, `identities`; sets `invites.accepted_by` to NULL; leaves `audit` rows (no FK). Owned bots block it (NO ACTION), which the app checks first with Q6.
    - Deleting a **session** (Q57, and the housekeeping Q62) removes the confidential clients' `refresh_tokens` and the session's `auth_codes` — the design's "a confidential client's token lives and dies with the SSO session".
    - Deleting a **service** (Q155) removes its `clients`.
13. **`UNLOGGED` table.** `throttle` trades durability for write speed; counters may vanish after a crash.
14. **Statement-level consistency.** Q141 reads three tables "in one statement, so they come from one snapshot"; Q123 and every multi-row `UPDATE … RETURNING` must be atomic.
15. **Read-your-writes across connections** immediately after commit (§3.1); there are no replicas.
16. **Multi-statement text batches and DDL in a transaction** (Q164): a migration and its `schema_migrations` row commit together or not at all.
17. **Connection-level settings from the URL**: `application_name` and arbitrary server settings (e.g. `search_path`, `statement_timeout`) are sent at connection start (`rust/src/db.rs:43-61`); the test harness uses `search_path` to give each test stack its own namespace in one database.

## 5. Migrations and lifecycle

**Schema creation and migration** (`rust/src/migrate.rs`, `src/migrate.ts`, DESIGN §8):
- Plain `.sql` files named `^\d{4}_[a-z0-9_]+\.sql$`, applied in name order; applied versions recorded in `schema_migrations`.
- Run at every server start and by every CLI command except `help` (`rust/src/cli.rs:402-406,434-439`; the `migrate` command does only this, the others also rotate a due signing key first), on one connection: take the session advisory lock (Q165) → `CREATE TABLE IF NOT EXISTS schema_migrations` → read applied versions → for each missing file `BEGIN; <file>; INSERT version; COMMIT` → unlock.
- **Expand-only**: never edit or drop an applied migration, so a process still running the previous build keeps working against the newer schema during a rolling deploy. Hence named column lists and no `SELECT *` in the Rust server.
- Both servers must be able to apply and share the schema; `conformance/mixed.test.ts` runs a copy of each on one database, both ways.

**Start-up** (`rust/src/main.rs:124-210`, `src/index.ts:67-92`): listen (everything but `/healthz` answers 503) → migrate → Q156 (refuse to start if a registered service needs an unset `API_KEY_PREFIX`) → key rotation (§3.2) → load keys (Q114) → note held services → ready → start jobs. Any database error restarts the sequence after a back-off; the process does not exit.

**Connection configuration** (`rust/src/db.rs:22-107`, `rust/src/pgurl.rs`, `docs/DEPLOYMENT.md:136-172`, `conformance/database.test.ts`):
- `DATABASE_URL` = `postgres://user:password@host:port/database?…` (also `postgresql://`), percent-encoded; refused at start if malformed, never echoed.
- **Pool: 5 connections per process**, opened lazily (`rust/src/db.rs:90`; `src/db.ts:5`). Each CLI invocation is its own process with its own pool.
- TLS by `sslmode`: `disable` (default) / `prefer` / `require` (no certificate check) / `verify-ca` / `verify-full`; `sslrootcert=<file>|system`, `sslcert` + `sslkey` (client certificate), `sslpassword`; `channel_binding`.
- Other URL keys: `connect_timeout`, `idle_timeout`, `max_lifetime`, `host`, `port`, `user`, `password`, `dbname`, `application_name`, `options`; any unknown key is a server setting. Fallbacks from `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, `PGSSLMODE`, `PGAPPNAME`, `PGOPTIONS`, `PGCONNECT_TIMEOUT`, `PGCHANNELBINDING`. A host that is a directory is a Unix socket (no TLS).
- Deployment: Postgres 16, a database and a role of auth's own, reachable only from auth's network (`docs/DEPLOYMENT.md:280-298`). Backups by `pg_dump` (DESIGN §9.6).

**Multi-process assumptions — yes, several processes share the database concurrently, and correctness depends on it:**
- Two server copies run side by side during every rolling deploy (possibly one Bun, one Rust); the break-glass CLI runs as a third process inside the same container. "Every piece of state lives in Postgres" (DESIGN §11); "nothing depends on which copy is up" (`rust/src/jobs.rs:1`).
- Cross-process coordination is entirely through the database: advisory locks, row locks, `SKIP LOCKED`, the shared throttle counters, the unique constraints, and the services revision.
- Per-process caches are validated against the database: services under their revision (Q140 every request, Q141 on change), signing keys for 60 s.
- An embedded, single-process store cannot replace this without changing the deployment model: the replacement must be a server (or otherwise multi-process safe) with real cross-process transactions and locks.

**Periodic jobs** (`rust/src/jobs.rs:39-97`, `src/jobs.ts`), in every process:
- Every 1 s: outbox delivery — Q123 (batch of 20), HTTP POSTs outside any transaction, then Q124/Q125/Q126 per row.
- At start and hourly: key rotation, then housekeeping. Housekeeping thresholds: `auth_codes` 1 h past expiry; `one_time_tokens` 1 day past expiry; `sessions` at expiry (idle or absolute); `refresh_tokens` at expiry or 1 day after revocation; unaccepted `invites` 30 days past expiry; `throttle` windows older than 1 day; `outbox` 7 days after delivery or give-up; `audit` after `AUDIT_RETENTION_DAYS` (default 365, 1–36500).
- Never purged: revoked `credentials` and `client_secrets`, accepted `invites`, `users`.

**Shutdown:** finish requests in flight, let the running job pass finish, wait ≤ 5 s for queued emails/alerts, close the pool (`rust/src/main.rs:212-226`).

**Tests reach the database directly** (`conformance/harness.ts:985-1075`): they create a schema per stack, seed and backdate rows with raw SQL (`now() + '-61 minutes'::interval`, explicit sequence ids), inspect rows, read `pg_stat_activity`, and drop the schema. The replacement needs an equivalent out-of-band admin path for the conformance suite.

## 6. Scale hints

- **Sizing stated by the design** (DESIGN §8, §10): dozens of users; database under 10 MB with `audit` dominating; about 0.1 queries/s at 50 active sessions; the server is budgeted 64 MB and half a CPU. Throughput is not the challenge; correctness under concurrency is.
- **Tables that grow:**
  - `audit` — one or more rows per sign-in, failure and change; kept a year by default. The only table that gets large.
  - `throttle` — one row per key; keys include client ids, IPs, user ids, typed-in unknown logins, per-sign-in ids, per-challenge ids, email addresses; purged after a day. The most write-intensive table (an upsert on most back-channel and sign-in requests); durability not required.
  - `refresh_tokens` — a new row per rotation for public clients; purged at expiry (30 days) or a day after revocation.
  - `sessions` (≤ 30 days), `auth_codes` (minutes), `one_time_tokens`, `outbox` (7 days), `credentials` (≤ 100 live per user per kind; revoked rows stay).
  - Bounded small: `services` ≤ 100, `clients` ≤ 5 per service, `signing_keys` ≈ 2–3 rows, `services_revision` 1 row.
- **Row sizes:** all small. Ids 30 bytes; digests 32 bytes; `outbox.token` ≈ 0.5 kB; `audit.detail` usually < 200 bytes (a service change lists URIs: up to a few kB); `user_agent` ≤ 512; `password_hash` ≤ 512; redirect URIs ≤ 10 × 1024 per client; `passkeys.credential_id` ≤ 1023 bytes. No large objects.
- **Hot paths (statements per request):**
  - Every routed request: Q140.
  - Signed-in browser/API request: Q52 (+ Q53 at most once a minute) + Q21 (admin check).
  - Token refresh — the dominant load, one per active session per 10 minutes: Q140, Q91, Q133, then one transaction of Q160\*, Q68, Q167, Q69, Q21, Q4, Q53 (or Q71 + Q66), then Q114 at most once a minute. (\* only for services registered in the database.)
  - Introspection of an API key / app password (apps cache 60 s; limit 600/min per client): Q140, Q91, Q133, Q138 × 1–2, Q86, Q87 (≤ once a minute), and Q133 × 1–2 on failure.
  - Password sign-in: Q140, Q133, Q2|Q3, Q134, Q31, then a transaction with Q131 (a per-user scan of `audit` through `audit_user`), Q54|Q55, Q129; then Q136. Dominated by 45–90 ms of argon2, not by the database.
  - Background: Q123 once a second per process (partial index `outbox_pending`); `/healthz` → Q168.
- **Performance-sensitive details:** the unique `bytea` lookups (Q52, Q69, Q86, Q78) must be index point reads; Q133 must be a single atomic round trip; Q140 should be as cheap as possible (a change counter would also serve as a push notification target); pool of 5 means long transactions (the 10,000-row imports, a blocked advisory lock) can starve requests.
- **Scans that are acceptable only because tables are small:** Q7/Q8 (no index for `LIKE` / `lower(name)`), Q75, Q80, Q90, Q94, Q88.

## 7. Hardest things to replicate without SQL (ranked)

1. **Refresh-token rotation and family revocation** (`rust/src/oauth.rs:416-480`, `rust/src/sessions.rs:144-172`): a shared lock on the client row, a per-family named lock taken *before* reading to exclude phantom inserts, a locking read across a LEFT JOIN that locks one side only (Q69) with six server-time flags, then conditional family-wide revocation or rotate-and-insert — all in one READ COMMITTED transaction shared by several processes.
2. **Cross-process locking vocabulary as a whole** (§3.3): session-scoped and transaction-scoped named locks, blocking and try; shared vs exclusive row locks; skip-locked; a designed lock order instead of deadlock handling; and CAS writes that depend on "block, then re-check the predicate against the committed row".
3. **The service registry** (`rust/src/registry.rs`): a per-request revision read; a single-row counter that is also the global write mutex; shared locks held by every grant, invitation, credential and token transaction against exclusive locks of a change; a snapshot-consistent three-table load (Q141); and hand-written cleanup across seven tables when a service or client goes (Q30, Q75, Q79, Q80, Q90, Q95, Q104, Q127) plus a cascade.
4. **Outbox leasing** (Q123): claim the oldest N due rows not claimed by anyone else, bump attempts and set a server-time lease, return them — one atomic statement over a partial index; enqueue (Q122) must be atomic with the change that caused it.
5. **Atomic rate limiting on server time** (Q133–Q138): insert-or-update whose update branch is conditional on the stored window versus the server clock, returning the new count and a computed retry-after; exponential back-off computed in the query; insert-if-absent as a once-only guard.
6. **Uniqueness beyond a primary key**: the partial, case-insensitive unique index on `lower(email)` (NULLs excluded), secondary unique keys on byte strings, upserts on composite keys with `EXCLUDED`, and violations reported **by constraint name** from inside a transaction that then rolls back (§3.4).
7. **Cascading deletes inside larger transactions** (§4.12): users → ten tables (one `SET NULL`, one blocking self-reference), sessions → tokens and codes; also triggered by bulk housekeeping deletes; always atomic with the audit and outbox rows written beside them.
8. **Signing-key rotation** (Q114–Q118): scalar and correlated subqueries (`max`, `min`, `count`, `EXISTS`), a self-referencing UPDATE, all on server time under a named lock.
9. **The few analytical reads**: keyset pagination with a three-column OR of prefix/case-insensitive matches, one variant joined to `access` (Q7, Q8); `COUNT(*) FILTER` on a JSON field (Q131); GROUP BY with MIN/MAX ordered by an aggregate (Q74); "all but the newest" by subquery (Q92); DISTINCT over an OR of two indexed columns (Q63).
10. **Server-evaluated time and parsing**: one clock for every process, transaction-stable `now()`, interval arithmetic with fractional seconds, and text → timestamp parsing/validation delegated to the server (Q169, Q170, Q83, Q89).
11. **Online, expand-only schema migration** with transactional DDL under a session lock, while processes built against the previous schema keep running with cached prepared statements.
